# Storage UNSEEN: Cloudflare R2 e Supabase

Supabase conserva login, utenti, opere, brani, duelli, voti e riferimenti ai file. I nuovi file viaggiano direttamente dal browser verso R2; nessun file attraversa Vercel o Supabase Storage.

## Configurazione applicata

- Progetto Supabase: `mpqphroecgfwonclmkyb`.
- Bucket privato `unseen-uploads`: upload temporanei e contenuti in revisione.
- Bucket `unseen-media`: copie approvate, accessibili tramite il Worker `https://unseen-media.unseen-deboshoot.workers.dev`. Entrambi i bucket hanno l'accesso pubblico nativo disabilitato.
- Edge Function Supabase `r2-media`: verifica identità e quote, firma upload, controlla i file, registra i riferimenti e gestisce moderazione/eliminazione.
- Worker Cloudflare: riproduzione pubblica con CORS, ETag, richieste Range e cache di cinque minuti. Pulizia automatica ogni ora al minuto 17.
- Unico amministratore dell'app: `deboshoot@gmail.com`, con il controllo centralizzato `is_unseen_admin()`. La dashboard include fotografie e musica.

## Invio e moderazione

Entrambe le tipologie richiedono login. Ogni account può prenotare cinque invii in 24 ore; anche i tentativi scaduti contano. Le immagini vengono ottimizzate nel browser: lato massimo 2400 pixel per foto, 1600 per copertine, WebP quando riduce il peso. Limiti effettivi: 5 MB per immagine e 30 MB per audio MP3/WAV.

1. Il browser invia solo descrizione e dimensioni alla funzione.
2. La funzione assegna percorsi temporanei e URL PUT firmati per cinque minuti, vincolati a MIME e byte.
3. Il browser carica i file direttamente su R2.
4. La conferma controlla dimensioni, MIME e firma iniziale del formato; congela copie separate dai percorsi modificabili dell'upload e registra una candidatura pending in una transazione.
5. L'admin vede foto e brani privati con URL GET a scadenza. L'approvazione copia i file nel bucket di pubblicazione e aggiorna i riferimenti nel database.
6. Rifiuto/eliminazione e pulizia usano una coda e blocchi per evitare di cancellare file ancora referenziati. Un file precedentemente approvato può restare in cache per un massimo di cinque minuti dopo la rimozione.

La verifica dei formati non è una scansione completa del contenuto. Il selettore di estratti da 30/40 secondi, transcodifica audio, miniature e statistiche aggregate sono lavori successivi: attualmente viene caricato il file audio scelto, fino a 30 MB. I contenuti rifiutati restano privati finché l'admin li elimina; non è imposta una conservazione arbitraria.

## File precedenti e passaggio in produzione

I 127 file già presenti in Supabase Storage restano dove sono e mantengono i propri URL. Non sono stati migrati o eliminati. Il frontend aggiornato non usa Supabase Storage come fallback.

Dopo un deploy verificato, `scripts/cutover-r2.mjs --apply` disabilita gli upload sul vecchio storage e gli inserimenti fotografici diretti degli utenti. Preserva letture pubbliche e gestione dei contenuti precedenti da parte dell'admin. Lo script richiede un verbale locale recente di verifica del frontend pubblico; `--rehearse` prova la modifica senza applicarla.

Il deploy usa il collegamento GitHub → Vercel già esistente: il push a `main` avvia il deploy. Le variabili frontend sono esclusivamente `VITE_SUPABASE_URL` e `VITE_SUPABASE_ANON_KEY`, già richieste dal progetto. Le chiavi R2 e la service role non devono mai entrare nel bundle o nel repository.

## Gestione da terminale

Eseguire dalla cartella `unseen-main`, con Node disponibile:

```text
node scripts/github-release-status.mjs
node scripts/check-r2.mjs
node scripts/setup-supabase-r2.mjs --verify
node scripts/test-r2-integration.mjs
```

L'ultima prova crea e rimuove dati di test: verifica upload reali, moderazione, audio Range e voto musicale. I verbali sono nella cartella ignorata `../debug.local/r2/`. Le credenziali sono nei file locali ignorati `.env.supabase.local` e `.env.cloudflare.local`; i segreti operativi sono configurati solo sui server.

`configure-r2.mjs` e `setup-supabase-r2.mjs --apply` servono per aggiornare la configurazione e il codice server; non riapplicare manualmente le migrazioni già registrate. Lo schema storico `supabase/music-arena.sql` è superato dal nuovo schema R2 e non va eseguito.

## Costi e crescita

R2 separa i file dal database, ma non offre spazio illimitato. Monitorare storage, operazioni R2, richieste Worker, database ed egress Supabase. Il Worker conta anche le richieste servite dalla sua cache; la cache evita letture R2, non azzera le richieste Worker. Le quote e le stime sono descritte in [ARCHITETTURA.md](./ARCHITETTURA.md). Per mantenere il budget a zero servirà un limite globale degli upload prima dell'esaurimento delle quote, oltre al limite per utente già attivo.
